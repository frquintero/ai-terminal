**AI-Coding-Agent:**

**Current Architecture (v2.0):**  
The system is split into **front-end** (`main.py` REPL) and **back-end** (Orchestrator). The REPL handles user terminal I/O and forwards queries to the Orchestrator. The Orchestrator controls logic and delegates command execution to a top-level **ToolExecutor** module (separate but under its command), which runs commands in an integrated shell terminal. It owns a unified database (`orchestrator.db`) managed via the Memory API, storing sessions, router_decisions, intention_cache, task_state, step_outputs, chat_history, llm_traces, and metrics. The flow starts with a deterministic Router (regex + FTS cache + fallback PLANNER) that classifies the query into [SHELL], [CACHED], [CHAT], or [PLANNER]. Depending on the route:  
- [CHAT] → Agent C (Narrator) responds directly.  
- [CACHED] → ToolExecutor + Agent C narrates.  
- [PLANNER] → Agent A (Planner) generates JSON plan → Agent B (Executor) translates to commands → Orchestrator sends to **ToolExecutor** → execution → Agent C narrates final output.  
Three LLM agents (A, B, C) operate with dynamic system prompts generated by the Orchestrator. Final output is sent back to the REPL for display.

**Agent A Current JSON Schema (to Orchestrator):**  
Agent A outputs **exactly one** of three formats:  
1. **Execution Plan**: `{"steps": [{"tool_name": "...", "intent": "...", "description": "..."}, ...]}`  
2. **Clarification**: `{"clarify": "Question to ask user"}`  
3. **Delegation to Chat**: `{"delegate_to_chat": "Reason"}`

**Problem (Issue):**  
High redundancy and overhead:  
- Agent C narrates in *all* routes, even when A could do it.  
- Multiple LLM hops (A → B → C) consume tokens, increase latency, and add complexity.  
- Router adds an unnecessary layer if the first agent can decide intelligently.  
- Strict role division creates needless handoffs and context fragmentation.  
- Current Agent A schema is **planning-only** — lacks narrative control.  
- Simple shell commands (e.g., `ls`) bypass B unnecessarily via [SHELL] or [CACHED].

**Proposed Solution: Simplified Architecture (no Router, no Agent C, strict role enforcement, unified "no-tools" semantics, rich output handling):**  
The Orchestrator removes the Router and Agent C. Every query from the REPL goes directly to **Agent A (Planner + Narrator only)**.  

**Agent A Responsibilities:**  
- **Plan** (when tools are needed).  
- **Narrate** (always — final user message).  
- **Never** generate or execute commands.  
- **Designs complete final narration** using placeholders that reference **future outputs of each step** — including scalars, lists, raw terminal output, or visual tables (e.g., `cal`).

**Agent B Responsibilities:**  
- **All command generation** — even for simple cases like `ls`.  
- Processes **one step at a time** from the plan.  
- Returns **only** executable command + **structured output schema** (via `tool_arguments` format) for Orchestrator to capture.  
- **No narration** — only command + expected output keys and types.

**Agent A New JSON Schema (to Orchestrator):**  
Agent A outputs **exactly one** of two formats:  

1. **No-Tools Response** (unified: direct answer or clarification):  
   ```json
   {"response": "Full natural language message to user"}
   ```  

2. **Execution Plan with Narration (requires tools):**  
   ```json
   {
     "steps": [
       {
         "tool_name": "shell",
         "intent": "list modified .py files",
         "description": "find . -name '*.py' -mtime 0",
         "output_keys": ["files", "count"]
       },
       {
         "tool_name": "shell",
         "intent": "show calendar",
         "description": "cal",
         "output_keys": ["calendar"]
       }
     ],
     "narration_template": "Found {count} Python files: {files}.\n\nHere is the current calendar:\n{calendar}"
   }
   ```  
   **Critical:**  
   - Placeholders like `{count}`, `{files}`, `{calendar}` **must match** `output_keys` declared per step.  
   - **Agent A does not compute values** — only declares **what** to show and **how** to render (text, list, raw block).  
   - **Agent B returns** structured `tool_arguments` with types:  
     ```json
     {
       "command": "find . -name '*.py' -mtime 0 | wc -l && find . -name '*.py' -mtime 0",
       "output_format": {
         "count": "int",
         "files": "list"
       }
     }
     ```
   - **Orchestrator** collects all step outputs → builds final variable map → fills `narration_template` **preserving formatting**.

**Execution Flow (Tool-Using Path):**  
1. Orchestrator → **Agent A** → receives full plan with `steps[]` and `narration_template`.  
2. Orchestrator **iterates steps** in order:  
   - Sends current step to **Agent B**.  
   - **Agent B** returns:  
     ```json
     {"command": "...", "output_format": {"key": "type"}}
     ```  
   - Orchestrator → **ToolExecutor** runs command → gets **raw stdout/stderr**.  
   - Orchestrator **parses raw output** using B’s `output_format`:  
     - `int` → parse number  
     - `list` → split lines  
     - `raw` → preserve full block (e.g., `cal`, `tree`)  
     - `table` → preserve ANSI formatting  
   - Stores in `memory/step_outputs` as structured values.  
   - Proceeds to next step.  
3. After **all steps consumed**, Orchestrator:  
   - Aggregates all `output_keys` into final variable map.  
   - **Fills** `narration_template` using real values, **preserving newlines, spacing, and terminal formatting**.  
   - Sends final message to REPL.

**Example – Rich Output (Lists + Raw Calendar):**  
User: *"Show me modified .py files and the current calendar."*  
→ Agent A outputs:  
```json
{
  "steps": [
    {"tool_name": "shell", "intent": "find modified .py", "output_keys": ["files", "count"]},
    {"tool_name": "shell", "intent": "show calendar", "output_keys": ["calendar"]}
  ],
  "narration_template": "Found {count} Python files modified today:\n{files}\n\nCurrent calendar:\n{calendar}"
}
```  
→ Step 1 → B → `find . -name '*.py' -mtime 0 | wc -l && find . -name '*.py' -mtime 0`  
→ ToolExecutor → raw output  
→ Orchestrator parses → `count=3`, `files="script1.py\nutil.py\nmain.py"`  
→ Step 2 → B → `cal`  
→ ToolExecutor → raw ASCII calendar  
→ Orchestrator stores as `calendar="     November 2025     \nSu Mo Tu ..."`  
→ Final assembly:  
```
Found 3 Python files modified today:
script1.py
util.py
main.py

Current calendar:
     November 2025     
Su Mo Tu We Th Fr Sa  
                   1  
 2  3  4  5  6  7  8  
...
```
→ Sent to REPL **with full formatting preserved**.

**Benefits:**  
- **Agent A = Full Narrator + Planner** — designs **complete, rich final response** using declarative placeholders.  
- **Agent B = Step-wise Command Engineer** — one step at a time, returns `tool_arguments` with structured output.  
- **Orchestrator = Smart Resolver + Formatter** — computes values **downstream**, preserves **lists, raw blocks, ANSI art, tables**.  
- **No premature narration** — full context available.  
- **All tool use via B** → strict roles.  
- Removes Router and Agent C → fewer LLM calls.  
- Fewer handoffs → lower latency and token usage.  
- Shell-first preserved via B → ToolExecutor.  
- Clean separation: **REPL = front-end**, **Orchestrator = back-end**, **ToolExecutor = execution engine**.
